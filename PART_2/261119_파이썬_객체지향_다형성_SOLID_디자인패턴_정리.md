## 🔑 오늘의 키워드

| 키워드 | 한 줄 정리 |
|---|---|
| **다형성 (Polymorphism)** | 하나의 명령(메서드 이름) → 객체마다 다른 결과 |
| **if-hell** | 종류를 `if/elif`로 묻는 코드. 종류 추가 시 분기 N곳 수정 |
| **오버라이딩** | 부모와 같은 이름의 메서드를 자식이 다시 정의 |
| **리스트 + for 문** | 여러 자식 객체를 한 리스트에 담아 `if` 없이 처리 |
| **NotImplementedError** | 부모 메서드에서 일부러 에러 → **호출 시점**에 구현 누락 발견 |
| **ABC / @abstractmethod** | 추상 클래스 → **객체 생성 시점**에 `TypeError`로 차단 |
| **추상 메서드** | 선언부(이름·매개변수)만 있고 바디(`...`/`pass`)는 비어 있는 메서드 |
| **덕 타이핑** | 상속 없어도 같은 이름의 메서드만 있으면 다형성 OK (파이썬 특징) |
| **hasattr()** | 객체에 속성/메서드가 있는지 확인 |
| **`__str__`** | `print(객체)` 시 출력 모양 정의 (연산자 오버로딩 입문) |
| **OCP** | 확장에는 열려 있고, 수정에는 닫혀 있어야 한다 |
| **SOLID** | SRP · OCP · LSP · ISP · DIP — 클래스 설계 5원칙 |
| **디자인 패턴** | 반복되는 설계 문제 + 검증된 해결 구조에 이름을 붙인 것 (GoF, 23개) |

## 1. 왜 다형성이 필요한가? — if 지옥

```python
def calc_price(kind, price):
    if kind == "전자제품":   return price + price * 5 // 100
    elif kind == "의류":     return price * 80 // 100
    elif kind == "식품":     return price + 3000
    else: raise ValueError(f"알 수 없는 상품 종류: {kind}")
# shipping_info(kind) 에도 똑같은 if/elif 가 반복됨
```

- 새 종류(도서) 추가 → `calc_price`, `shipping_info` **둘 다 수정**. 한 곳이라도 빠지면 버그
- 상품 30종 × 분기 함수 5개 = `elif` 150개 😱

| if 문 방식 | 다형성 방식 |
|---|---|
| 부르는 쪽이 종류를 **다 알아야** 함 | 부르는 쪽은 **메서드 이름만** 알면 됨 |
| 새 종류 → **기존 코드 수정** | 새 종류 → **클래스만 추가** |

> 💡 사실 이미 쓰고 있던 다형성: `len("abc")`, `len([1,2])`, `3+4`, `"a"+"b"`

## 2. 다형성의 핵심 공식: 오버라이딩 + 리스트 + for

```python
class Product:
    def __init__(self, name, price):
        self.name, self.price = name, price

class Electronics(Product):
    def final_price(self):  return self.price + self.price * 5 // 100
    def shipping_info(self): return "설치 기사 방문"

class Book(Product):                     # 새 종류 = 클래스 하나 추가
    def final_price(self):  return self.price * 90 // 100
    def shipping_info(self): return "무료 배송"

cart = [Electronics("노트북", 1_200_000), Book("파이썬 입문", 30_000)]
for item in cart:                        # 종류를 묻지 않는다 (if 0개)
    print(item.name, item.final_price(), item.shipping_info())

total = sum(item.final_price() for item in cart)   # 한 줄 합계
```

- 파이썬이 `item`의 **실제 클래스**를 보고 알맞은 메서드를 찾아감 → 판단을 파이썬에게 맡김
- 새 클래스 추가해도 **for 문은 한 글자도 안 고침** (= OCP)

## 3. 자식에게 구현 강제하기

**문제**: 자식이 오버라이딩을 깜빡하면 부모 기본 동작이 **조용히** 실행됨 → 버그 발견이 늦음

### ① `NotImplementedError` — 호출할 때 에러

```python
class Animal:
    def speak(self):
        raise NotImplementedError(f"{type(self).__name__}에는 speak() 정의가 필요합니다.")
```

### ② `abc` 모듈 — 객체 만들 때 에러 (더 빠름)

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...          # ... = "틀만 있고, 바디는 자식이 정의해"

class Broken(Shape): pass
Broken()   # TypeError: Can't instantiate abstract class Broken ...
```

| | 에러 시점 | 에러 종류 |
|---|---|---|
| `NotImplementedError` | 메서드 **호출** 시 | `NotImplementedError` |
| `@abstractmethod` | 객체 **생성** 시 | `TypeError` |

> 부모에 직접 구현한 메서드(예: `settle_amount()`)는 안에서 `self.fee()`를 불러도 **자식마다 다르게 동작**한다.

## 4. 덕 타이핑 (Duck Typing)

> "오리처럼 걷고 꽥꽥거리면, 그것은 오리다."

```python
class Duck:  
    def sound(self): print("꽥꽥")
class Robot: 
    def sound(self): print("삐빅")
class Rock: pass                          # sound() 없음

for t in [Duck(), Robot(), Rock()]:
    if hasattr(t, "sound"):  t.sound()    # 메서드 존재 확인
    else: print(f"{type(t).__name__}: 소리를 낼 수 없어요")
```

- 파이썬은 "무슨 클래스냐"가 아니라 **"그 메서드가 있냐"**만 본다 (Java와 다른 점)
- 장점: 유연함 (외부 파트너 클래스도 그대로 끼워 넣기 가능)
- 단점: 메서드가 없으면 **실행 중에** 에러 → `hasattr()` / ABC 로 보완

## 5. `__str__` — print 모양 바꾸기

```python
class Cat:
    def __init__(self, name): self.name = name
    def __str__(self): return f"🐱 귀여운 고양이 {self.name}"

print(Cat("나비"))   # 🐱 귀여운 고양이 나비   (없으면 <__main__.Cat object at 0x...>)
```

- `print()`라는 하나의 명령이 클래스마다 다른 결과 → 이것도 다형성
- 다음 단원 **연산자 오버로딩**(`__add__` 등)의 입문

## 6. 실습 정리: 결제 수단 정산 리팩터링

| 클래스 | `fee()` | `approve_message()` |
|---|---|---|
| `CardPayment` | `amount * 25 // 1000` | [카드] 카드사 승인 완료 |
| `EasyPayment` | `amount * 18 // 1000` | [간편결제] 앱 푸시 승인 완료 |
| `BankTransfer` | 500 | [계좌이체] 입금 확인 대기 |
| `PointPayment` *(신규)* | 0 | [포인트] 즉시 차감 완료 |

- 부모 `Payment`가 **약속**(fee, approve_message)을 정하고, `settle_amount()`만 직접 구현
- 포인트 추가 시 수정한 곳: **클래스 1개 + 리스트 1줄**, `settle()` 함수는 0줄
- 같은 패턴: `BaseClient` → `OpenAIClient / GeminiClient / ClaudeClient / LlamaClient` + `ask_all()`
- `BotManager`는 봇을 **상속하지 않고 포함**(composition, has-a)해서 `broadcast()`로 일괄 호출

## 7. 클래스 설계 5원칙 S.O.L.I.D

> 파이썬엔 `interface` 키워드가 없다 → `ABC` 추상 클래스로 "반드시 구현하라"는 약속을 만든다.

| 원칙 | 핵심 질문 | 위반 증상 → 해결 |
|---|---|---|
| **S** SRP 단일 책임 | 이 클래스를 바꿀 이유가 둘 이상인가? | 계산+출력+저장 한 클래스 → **클래스 분리** |
| **O** OCP 개방-폐쇄 | 기능 추가 때 기존 코드를 고치는가? | `if/elif` 증가 → **추상 클래스 + 다형성** |
| **L** LSP 리스코프 치환 | 자식으로 바꿔 넣어도 결과가 같은가? | `Square(Rectangle)` 넓이 깨짐 → **공통 추상 타입** |
| **I** ISP 인터페이스 분리 | 안 쓰는 메서드를 억지로 구현하는가? | 2D 도형의 `volume()` → **작은 인터페이스 + 다중 상속** |
| **D** DIP 의존성 역전 | 구체 클래스를 직접 생성하는가? | `self.db = MySQL()` → **추상화 + 의존성 주입** |

**포인트만 콕**
- **책임 = 변경의 이유**. 메서드가 하나여야 한다는 뜻이 아님
- LSP의 is-a는 현실 분류가 아니라 **행동(약속)이 같은지**로 판단. 반환 타입을 바꾸거나 매개변수 조건을 더 엄격하게 하면 안 됨
- `NotImplementedError`로 때우는 메서드가 보이면 → ISP·LSP 위반 의심
- DIP: `PasswordReminder → MySQL` 에서 `PasswordReminder → 인터페이스 ← MySQL`로 **방향 역전**, 테스트 땐 `FakeConnection` 주입

```python
# DIP 예시 (생성자 주입)
class DBConnection(ABC):
    @abstractmethod
    def connect(self): ...

class PasswordReminder:
    def __init__(self, db: DBConnection):   # 구체 클래스 대신 추상화를 받음
        self.db = db
```

> ⚠️ 과유불급: 작은 스크립트까지 SOLID를 엄격히 적용하면 클래스만 늘어난다. 변경이 잦은 곳부터!

## 8. 디자인 패턴 (알고만 있으면 OK)

> 모든 코드가 디자인 패턴을 적용하는 것은 아니다. **문제가 생겼을 때** 꺼내는 도구.

| 분류 | 관심사 | 패턴 | 한 줄 요약 | 파이썬다운 대안 |
|---|---|---|---|---|
| 생성 | 어떻게 **만들까** | Singleton | 객체를 하나만 만들어 공유 (`__new__`) | 모듈 |
| | | Builder | 복잡한 객체 단계별 조립 (`return self` 체이닝) | 키워드 인자, `dataclass` |
| | | Factory | 생성 코드를 한곳에 모음 | 클래스를 담은 딕셔너리 |
| 구조 | 어떻게 **조합할까** | Adapter | 안 맞는 인터페이스를 변환기로 감쌈 | 그대로 사용 |
| | | Decorator | 객체를 감싸 기능 덧붙임 (여러 겹 가능) | 함수엔 `@데코레이터` |
| 행위 | 어떻게 **협력할까** | Observer | 상태 변화 → 구독자에게 자동 통지 | 콜백 함수 리스트 |
| | | Strategy | 알고리즘을 객체로 분리해 교체 | 함수 전달 (`key=`) |

- 장점: 검증된 구조, 개발자 간 **공통 언어**, 문제 발생 시 가이드
- 단점: 클래스가 늘고 흐름이 흩어져 읽기 어려움, 과잉 설계(over-engineering) 위험
- 패턴을 쓰는 조직이면 **팀 규칙대로 철저히** (일관성 우선)
- 대부분의 패턴은 **OCP, DIP를 구현하는 구체적 방법**
- 팩토리 = "**무엇을** 만들지", 전략 = "**어떻게** 처리할지"

## 9. 오늘 배운 전체 흐름 한눈에 보기

```python
# =====================================================================
# 결제 수단 정산 시스템 — 오늘 배운 개념을 하나의 코드로
#   if-hell → 다형성 → 추상 클래스 → 덕 타이핑 → __str__ → SOLID(DIP)
# =====================================================================
from abc import ABC, abstractmethod


# ---------------------------------------------------------------------
# [1] 추상 부모 클래스 — "모든 결제 수단은 이 약속을 지켜라"
#     ABC 를 상속 → 직접 객체 생성 불가, 설계도(인터페이스) 역할
# ---------------------------------------------------------------------
class Payment(ABC):
    def __init__(self, amount):
        self.amount = amount                    # 공통 속성: 결제 금액

    @abstractmethod                             # 자식이 반드시 구현해야 하는 메서드
    def fee(self): ...                          # ... = 선언만, 바디는 자식이 정의

    @abstractmethod
    def approve_message(self): ...

    def settle_amount(self):                    # 부모가 직접 구현한 공통 로직
        return self.amount - self.fee()         # self.fee() 는 자식마다 다르게 동작 (다형성!)

    def __str__(self):                          # print(객체) 했을 때 보일 모양
        return (f"{self.approve_message():22} 결제 {self.amount:>8,}원 "
                f"수수료 {self.fee():>5,}원")


# ---------------------------------------------------------------------
# [2] 자식 클래스 — 같은 메서드 이름, 각자의 방식으로 오버라이딩
# ---------------------------------------------------------------------
class CardPayment(Payment):
    def fee(self): return self.amount * 25 // 1000        # 2.5%
    def approve_message(self): return "[카드] 카드사 승인 완료"

class EasyPayment(Payment):
    def fee(self): return self.amount * 18 // 1000        # 1.8%
    def approve_message(self): return "[간편결제] 앱 푸시 승인 완료"

class BankTransfer(Payment):
    def fee(self): return 500                             # 건당 500원
    def approve_message(self): return "[계좌이체] 입금 확인 대기"

# 신규 결제 수단 추가 → 클래스만 추가! 기존 코드 수정 0줄 (OCP)
class PointPayment(Payment):
    def fee(self): return 0
    def approve_message(self): return "[포인트] 즉시 차감 완료"


# ---------------------------------------------------------------------
# [3] 구현 강제 확인 — fee() 를 빠뜨리면 "객체 생성 시점"에 TypeError
#     (NotImplementedError 였다면 settle_amount() "호출 시점"에야 에러)
# ---------------------------------------------------------------------
class GiftCardPayment(Payment):
    def approve_message(self): return "[상품권] 잔액 차감 완료"
    # fee() 누락!

try:
    GiftCardPayment(10_000)
except TypeError as e:
    print("❌ 객체 생성 차단:", e)


# ---------------------------------------------------------------------
# [4] 덕 타이핑 — Payment 를 상속하지 않은 외부 파트너 클래스
#     같은 이름의 메서드(fee, approve_message, settle_amount)만 있으면 OK
# ---------------------------------------------------------------------
class PartnerCoupon:
    def __init__(self, amount): self.amount = amount
    def fee(self): return 0
    def approve_message(self): return "[제휴쿠폰] 파트너사 승인"
    def settle_amount(self): return self.amount

class Rock:          # 메서드가 하나도 없는 객체 → hasattr 로 걸러낸다
    pass


# ---------------------------------------------------------------------
# [5] SOLID 적용
#   SRP: 정산(계산) 책임과 출력(리포트) 책임을 분리
#   DIP: Settlement 는 구체 클래스가 아닌 Reporter(추상화)에 의존 → 생성자 주입
# ---------------------------------------------------------------------
class Reporter(ABC):
    @abstractmethod
    def report(self, total_fee, total_settle): ...

class ConsoleReporter(Reporter):        # 나중에 HtmlReporter, JsonReporter 로 교체 가능
    def report(self, total_fee, total_settle):
        print(f"총 수수료: {total_fee:,}원 / 총 정산 금액: {total_settle:,}원")

class Settlement:
    def __init__(self, reporter: Reporter):     # 의존성 주입(DI)
        self.reporter = reporter

    def settle(self, payments):
        """결제 수단을 '묻지 않는' 정산 — if/elif, isinstance 없음"""
        valid = [p for p in payments if hasattr(p, "settle_amount")]  # 덕 타이핑 안전장치
        for p in valid:
            print(p.approve_message(), f"{p.amount:,}원")             # 하나의 명령, 여러 결과
        total_fee = sum(p.fee() for p in valid)
        total_settle = sum(p.settle_amount() for p in valid)
        self.reporter.report(total_fee, total_settle)
        return total_fee, total_settle


# ---------------------------------------------------------------------
# [6] 실행 — 여러 종류의 객체를 리스트 하나에, for 문 하나로
# ---------------------------------------------------------------------
payments = [
    CardPayment(100_000),
    EasyPayment(50_000),
    BankTransfer(200_000),
    PointPayment(30_000),       # 신규 추가: 리스트에 한 줄만
    PartnerCoupon(10_000),      # 상속 없는 덕 타이핑 객체
    Rock(),                     # 메서드 없음 → hasattr 로 제외
]

print(CardPayment(100_000))     # __str__ 덕분에 보기 좋은 출력
Settlement(ConsoleReporter()).settle(payments)
# 총 수수료: 3,900원 / 총 정산 금액: 386,100원
```

### ✅ 전체 리마인드
- 다형성 = **하나의 명령, 여러 결과** → 오버라이딩 + 리스트 + for 로 **if 지옥 탈출**
- `@abstractmethod`는 **객체 생성 시점**에 구현을 강제한다
- 파이썬은 **덕 타이핑**이라 상속 없이도 다형성이 된다 (`hasattr`로 보완)
- `__str__`로 `print()` 결과를 바꿀 수 있다
